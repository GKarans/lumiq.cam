## Jaunākais Auth diagnostikas statuss (2026-09-30)

Production SQL Editor tika veikta tikai-lasāma pārbaude: `sync_own_account` ir `SECURITY DEFINER`, `lumiq_api_owner` ir funkcijas īpašnieks, `auth.uid()` izpilde un vajadzīgās tabulu/kolonnu tiesības ir piešķirtas, bet šai lomai trūkst `USAGE` uz `auth` shēmas. Tas izskaidro, kādēļ paroles formas secīgais konta sinhronizācijas solis varēja atgriezt 403. DB lomas/grants iepriekšējais audits nebija pārbaudījis šo atsevišķo funkcijas īpašnieka shēmas tiesību.

Repo migrācija `047-sync-account-auth-schema-usage.sql` sākotnēji mērķēja tikai `lumiq_api_owner`. Pēc 2026-10-01 tikai-lasāmā audita īpašnieks apstiprināja paplašinājumu uz sešām vēsturiskajās migrācijās Auth/JWT izmantojošām RPC īpašnieku lomām: `lumiq_api_owner`, `lumiq_admin_owner`, `lumiq_billing_owner`, `lumiq_support_owner`, `lumiq_session_owner`, `lumiq_preview_owner`; katrai tikai `USAGE ON SCHEMA auth`. Atjauninātā migrācija ir lokāli testēta, bet Production datubāzē nav pielietota. Tā pirms izmaiņas pārbauda visu sešu lomu esamību un izpildītāja `GRANT OPTION`, pretējā gadījumā izmet kļūdu. Iepriekšējais aizsargātais Production mēģinājums tika atcelts: Supabase `postgres` nav `USAGE WITH GRANT OPTION` un nevar `SET ROLE supabase_admin`; ledger `001–046`, 047 nav piemērota. 2026-09-30 pieteikums `SU-490493` attiecas tikai uz API lomu. Supabase Support lapa 2026-10-01 rāda jauna pieprasījuma “Support request sent”, taču UI neuzrāda sūtītā pieprasījuma saturu vai numuru, tādēļ paplašinātā tvēruma iesniegšana nav pierādīta. Atbalsta piekļuve projektam izslēgta. Shēmas īpašumtiesības, tabulu grants un `BYPASSRLS` nemainīt. Pēc Supabase atbalstītas atbildes atkārtot 047, sešu lomu runtime pārbaudi un paroles/Auth plūsmu QA.

Verifikācija pēc koda izmaiņām: pilnais `npm run verify` `185/185` testi un build ar 60 publiskajiem failiem. Production inspectors ir tikai-lasāms. DB granta piešķiršana netika pabeigta; iepriekšējā migrācijas transakcija tika atcelta. Worker deploy nav veikts.

Paplašināts tikai-lasāmais Production Auth grant audits 2026-10-01: izsaukts `production-secrets.ps1 inspect-production-auth-grants`, kas lieto tikai DPAPI glabātuves kredenciāli un piesprauž projektu `baqebydtinysosueksgr`. `auth` ACL satur `USAGE` tikai Supabase lomām (`anon`, `authenticated`, `service_role`, `supabase_auth_admin`, `dashboard_user`, `postgres` u.c. īpašniekiem); visām 11 Lumiq lomām ar sufiksu `*_owner` (`lumiq_admin_owner`, `lumiq_api_owner`, `lumiq_billing_owner`, `lumiq_guest_owner`, `lumiq_job_owner`, `lumiq_limit_owner`, `lumiq_payment_owner`, `lumiq_preview_owner`, `lumiq_session_owner`, `lumiq_storage_owner`, `lumiq_support_owner`) `auth_schema_usage=false`, lai gan `auth.uid()` funkcijas EXECUTE paliek true. Vēsturiskās migrācijas tieši piešķir `USAGE ON SCHEMA auth` sešiem JWT/RPC īpašniekiem: API (`014`), admin (`036`), support (`037`), session (`038`), preview (`040`) un billing (`041`). Tas norāda uz plašāku ACL neatbilstību paroles RPC vienu, bet patiesā kļūmes izcelsme (t.sk. saistība ar DB upgrade) nav pierādīta. Ledger joprojām `001–046`, 047 nav pielietota; `postgres` nevar dot grant-option vai `SET ROLE supabase_admin`. Sākotnējais Support pieteikums `SU-490493` sedz tikai API lomu. Pēc īpašnieka apstiprinājuma migrācija `047` lokāli paplašināta uz sešām Auth RPC lomām un Production/Recovery pārbaudes salāgotas; Production nav mainīts. Support UI 2026-10-01 rāda jauna pieteikuma iesniegšanas apstiprinājumu, bet saturu un ticket ID nepierāda. Nekāds grants, migrācija, shēmas īpašumtiesības vai `BYPASSRLS` Production vidē nav mainīts.
